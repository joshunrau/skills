Review of the selected code along up to three axes:

- **Standards**: does the code follow the documented coding standards?
- **Spec**: does the code conform to the spec?
- **Justified Complexity**: is the code more complicated than it's evident purpose justifies?

All axes run as **parallel sub-agents** so they don't pollute each other's context, then this skill aggregates their findings.

## Process

### 1. Resolve the Selection

If the user provided specific path(s), the selection is every file under them; if the user provided a git ref, confirm it resolves with `git rev-parse <ref>`, then, from the repository root, take the code files changed since the merge base, working tree included, deleted files dropped:

  ```sh
  git diff --name-only --diff-filter=d $(git merge-base <ref> HEAD)
  git ls-files --others --exclude-standard
  ```

Drop autogenerated code: `**/prisma/generated/`, and `src/route-tree.ts`.

Done when the file list is written out and `wc -l` over it gives the total. An empty list should fail here.

### 2. Spawn the Subagents in Parallel

Issue both sub-agent calls together, in the foreground, and aggregate the reports they return.

### Axis 1: Standards

The following file documents how code should be written: `docs/CODING_GUIDELINES.md`. The Standards subagent should read it in full.

On top of `CODING_GUIDELINES.md`, the Standards axis always carries the **smell baseline** below. Each smell is a labelled heuristic,never a hard violation. 

Each smell reads _what it is_ → _how to fix_; match it against the diff:

- **Mysterious Name**: a function, variable, or type whose name doesn't reveal what it does or holds. → rename it; if no honest name comes, the design's murky.
- **Duplicated Code**: the same logic shape appears in more than one hunk or file in the change. → extract the shared shape, call it from both.
- **Feature Envy**: a method that reaches into another object's data more than its own. → move the method onto the data it envies.
- **Data Clumps**: the same few fields or params keep travelling together (a type wanting to be born). → bundle them into one type, pass that.
- **Primitive Obsession**: a primitive or string standing in for a domain concept that deserves its own type. → give the concept its own small type.
- **Repeated Switches**: the same `switch`/`if`-cascade on the same type recurs across the change. → replace with polymorphism, or one map both sites share.
- **Shotgun Surgery**: one logical change forces scattered edits across many files in the diff. → gather what changes together into one module.
- **Divergent Change**: one file or module is edited for several unrelated reasons. → split so each module changes for one reason.
- **Message Chains**: long `a.b().c().d()` navigation the caller shouldn't depend on. → hide the walk behind one method on the first object.
- **Middle Man**: a class or function that mostly just delegates onward. → cut it, call the real target direct.
- **Refused Bequest**: a subclass or implementer that ignores or overrides most of what it inherits. → drop the inheritance, use composition.

**Standards sub-agent prompt** should include:

- The full diff command and commit list (if applicable).
- The `docs/CODING_GUIDELINES.md` file, plus the smell baseline from step 3 pasted in full (the sub-agent has no other access to it).
- The brief: "Report, per file/hunk where relevant, (a) every place the diff violates a documented standard: cite the standard (file + the rule); and (b) any baseline smell you spot: name it and quote the hunk. Distinguish hard violations from judgement calls: documented-standard breaches can be hard, but baseline smells are always judgement calls, and a documented repo standard overrides the baseline. Skip anything tooling enforces. Under 2000 words."

### Axis 2. Spec

The following file documents the full application spec: `SPEC.md`

**Spec sub-agent prompt** should include:

- The diff command and commit list (if applicable).
- Instructions to read `SPEC.md` in full.
- The brief: "Report: (a) anything that contradicts them spec, (b) regressions in terms of the spec. Quote the spec line for each finding. Under 2000 words."

### Axis 3. Justified Complexity

The Justified Complexity axis carries the **smell baseline** below:

- **Workaround for a safe assertion.** A rewrite larger than the `as` or `!` it avoids, when the fact holds for every input the function admits. Lines, plus a reader checking a guard that cannot fire. AGENTS.md allows the assertion when no rewrite of similar size removes it.
- **Defensive check inside trusted code.** Re-validation of data the system wrote or already validated at the boundary. A reader wondering which caller can violate it.
- **Helper with one caller** whose body reads as well in place. A jump for the reader, and a name to keep true.
- **Abstraction with one user.** A generic, parameter, option or interface with exactly one concrete use. The reader learns a general thing to understand a specific one.
- **Code made barbarous by a rule.** Code whose shape exists to satisfy a guideline or a lint rule rather than the problem. Name the rule; the finding goes in that rule's group.

### 3. Aggregate

Present the two reports under `## Standards` and `## Spec` headings, verbatim or lightly cleaned. Do **not** merge or rerank findings, because the two axes are deliberately separate (see _Why two axes_).

End with a one-line summary: total findings per axis, and the worst issue _within each axis_ (if any). Don't pick a single winner across axes: that's the reranking the separation exists to prevent.

## Why two axes

A change can pass one axis and fail the other:

- Code that follows every standard but implements the wrong thing → **Standards pass, Spec fail.**
- Code that does exactly what the issue asked but breaks the project's conventions → **Spec pass, Standards fail.**

Reporting them separately stops one axis from masking the other.
